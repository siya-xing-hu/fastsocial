# 目标账号短画像与批量监听

日期：2026-09-23

用户确认：简介＋最近 20 条帖子冷启动；画像要短；不记录 token 用量；不建立失败恢复队列；失败保留监听偏移量，下次定时补齐。X 获取、AI 分析各最多重试一次。Cookie 直接随机选，重试优先换另一份，不记录使用次数。

## 数据与画像

继续模拟 X 网页的浏览器请求，Cookie 和 CSRF 只发到 x.com，不使用 X 开发者 API。分别读取网页的 UserTweets 与 UserRepliesTimeline 分页，合并去重，覆盖网页可访问的原创、引用、转发和回复。账号简介通过 UserByScreenName 读取，缓存 24 小时。

首次学习简介和最近 20 条帖子；同账号按稳定 X 用户 ID 共享画像。新规则只建立历史基线，不通知历史帖；已有规则保留原监听偏移量。手动测试不会保存正式画像或推进进度。

画像为四个可选短段：背景、主题、用语、近况，连标签和换行最多 250 字。每段只接受单个对象，多个主题或用语合并为一行短文，不使用数组。推断保留限定语，不能因为监听条件提到 Codex，就把该账号的 reset 全解释成 Codex。近期话题 7 天过期，推断记忆 30 天未得到新证据时不再传入；重复证据不刷新有效期。用户可修正或清空画像。

SQLite 保存简介、当前画像与版本、事实证据 ID、帖子原文、最近批次状态和判断。常规调用只携带短画像、本批新帖及少量相关证据，不传完整历史。普通原文保留 30 天；尚未处理或用于画像的证据保留。画像的旧版本不单独归档。

## 每个监听周期

1. 按各规则上次成功处理的帖子 ID 读取完整新增窗口，分别翻页抓取帖子和回复，再合并去重。排除置顶指令，避免旧置顶导致误停。
2. 抓到的原文先落库；只有抓取和分析完整成功后才提交监听偏移量。
3. 同账号本次到期的规则共享读取和 AI 分析，未到期规则不提前推进。
4. 按最多 30 帖和估算 8,000 输入 token 分批，预算包含指令、规则、短画像和上下文。估算只用于分批，不记录用量或账单。超长单帖不截断，超预算时报错保留进度。
5. 每批一次 AI 调用，同时返回逐帖判断和画像更新；画像没有新信息时返回 null。跨批携带短画像和最近两条原文，必要时补充至多两条画像证据。多批中出现不确定条目时，在最终短画像下做至多一次可容纳的复核。
6. 输出严格校验每条规则对应的帖子 ID、漏项、重复项、理由、证据 ID 和画像长度。结果区分命中、未命中、不确定。不确定不发通知。
7. 命中内容通过现有 Telegram 配置通知；消息链接由真实保存的帖子构建。相对时间以发帖时刻为参照，保留未知时区或具体时刻的不确定性。
8. 全轮成功后在短 SQLite 事务里提交画像、判断和各规则偏移量，网络请求不占数据库事务。

## 失败与重试

每次 X 网页请求随机选择一份可用 Cookie，不统计其使用次数。请求失败后最多重试一次，有其他 Cookie 时换一份；只有一份且不是鉴权失败时允许原 Cookie 重试。明确鉴权失效标记 invalid，普通 403、404、网络错误不会把 Cookie 判死。用户明确选择某 Cookie 的连通性测试只检查该 Cookie。

AI 请求失败、输出截断或结果校验不通过，最多重试一次。校验失败需区分字段结构、缺少证据、未知证据和长度错误；重试附加具体的短纠错说明，不携带整份错误输出。8,000 输入 token 估算预算内预留纠错说明空间。二次失败结束本轮，保留偏移量，下一次按原配置间隔重新获取和分析。没有重试队列、退避调度或分页断点恢复。

通知失败也不推进偏移量，下次定时补偿。已确认发送成功的“规则 ID＋帖子 ID”落库去重。网络超时或发送后进程崩溃可能导致结果不确定，不能承诺严格恰好一次投递。

分页遇到结构变化、游标循环或每条时间线达到 50 页仍未覆盖边界时报错，保留偏移量；不把部分窗口标成成功。删除或平台未返回的内容不在可保证范围内。

同账号串行执行，防止画像覆盖。执行期间规则若被编辑、禁用或删除，则停止提交旧配置结果。

## 设置页

- 列表显示获取、分析、命中、不确定、待处理数量和失败阶段，不显示 token 用量。
- “画像”可查看简介、短画像、版本、证据原文，支持修正和清空。
- “批量测试”读取最近 20 条，用同一套批量提示词和校验逻辑，展示逐帖原因和证据；不发 Telegram、不保存正式画像、不推进监听偏移量。
- 输入、规则、模型配置和画像版本相同的手动测试缓存 24 小时，避免重复模型调用。
