# 架构与数据约定

## 模块职责

| 位置 | 职责 |
| --- | --- |
| `apps/extension/src/pages/option/` | 设置页与服务管理入口 |
| `apps/extension/src/pages/assistant/` | 对话、命令选择、草稿卡片 |
| `apps/extension/src/assistant/` | X 页面上下文、草稿校验、账号隔离的会话持久化 |
| `apps/extension/src/background/` | 扩展消息、服务调用、请求超时与错误转换 |
| `apps/extension/src/components/ui/` | 共享操作按钮、开关、确认交互 |
| `apps/server/src/configuration/` | 账号、配置关联、每日请求额度 |
| `apps/server/src/assistant/` | Skill 文件、目录、AI 对话、发帖权限 |
| `apps/server/src/workflows/` | 单用户／首页监听、有序动作、批次进度和恢复 |
| `apps/server/src/following/` | 按执行账号隔离的关注关系、画像与异步更新 |
| `apps/server/src/adapters/x/`、`outreach/x-client.ts` | X 内容读取、关系确认和互动请求 |
| `packages/contracts/src/` | 前后端共享类型与协议 |

新增接口先定义契约，再补服务和调用端。HTTP 路由负责参数验证，业务过程在 service / runner，数据库读写在 repository；不要把 X 请求和 AI 编排堆进 Vue 组件。

## 保存位置与离线行为

浏览器保存插件基础设置、翻译偏好、DeepL 密钥、AI 翻译指令，以及按账号分开的聊天历史和草稿。后端 SQLite 保存管理账号、凭证、配置关系、模型设置、监听和关注记录。数据库位于 `.data/fastsocial.db`，不要提交实际内容。

后端在线时，账号关联决定启用范围；未知账号不继承其他账号设置。后端离线时，基础插件使用浏览器默认配置，不按账号区分，不把离线当作数据库数据为空。Google / DeepL 基础翻译保持独立。浏览器配置迁移只迁移浏览器负责的内容。

## Skills 与画像

内置 Skill 模板：`apps/server/src/assistant/skills/{summary,post,reply}/SKILL.md`。运行时正文：`.data/skills/<名称>/SKILL.md`；数据库只管理基本信息、路径、启用状态。完整 Skill 说明任务、边界、材料处理、过程、输出和校验，设置页直接显示文件原文。备份数据库时同时备份 Skill 文件。

三个 Skill 分别处理总结、发帖、回复；账号 Profile 决定语言、身份、风格与边界。AI 翻译使用独立指令，不恢复旧 Prompt 模板管理作为新的主架构。变量采用 `{input}`、`{reply}`、`{{_tl_}}`，不添加其他同义变量。

侧边聊天是连续会话，Skill 只决定当前任务，切换 Skill 不清空上下文。普通讨论、解释和追问不强制调用 Skill，也不套用发布字数限制或读取发帖权限；自然语言明确要求生成文案或修改上一版时才匹配任务，显式 `/summary`、`/post`、`/reply` 优先。三个 Skill 全部停用时仍可普通聊天，不能绕过停用状态调用 Skill。普通对话响应不带 `skill` / `draft`，前端显示正常段落。

浏览器按账号、会话保存消息及当时的 Skill，用户消息另存页面素材快照 `reference`；生成卡片的 `context` 继续只负责账号／目标／编辑器填入校验。历史素材每条最多 16,000 字符，超出时优先保留选中内容、原帖、草稿，再保留能容纳的时间线帖子，并标记 `truncated`。请求最多携带最近 24 条消息，正文与素材合计最多 60,000 字符；优先保留对话正文，重复素材只发一次。后端按时间顺序组装历史，再附本轮页面和用户要求，不能把新页面当成旧总结的来源。旧会话的文本继续可用，但无法补回当时未保存的页面。新会话不带旧消息，账号之间不共享历史。

指定用户监听只支持单个用户。监听执行不自动生成或更新画像，包括首次执行和任务结束；判断和回复只使用已保存的有效画像，无画像时依据 Profile 与帖子判断。列表人形图标打开画像，手动点击“更新画像”并确认后，重新读取最新 Profile 和用户 Post 的首个分页，取其中最新最多 10 条非转发 Post，从空画像重新构建；取材、提示词和输出字段与关注列表共用。输入超预算时减少较旧样本，不截断原帖。一次更新只启动一轮画像生成，成功后保存，失败保留旧画像，不改变监听已处理记录。关注列表仍在新增关注后自动生成画像，其画像任务异步运行，失败只影响画像状态，不把已确认的关注改成失败。监听中新关注的用户立即落库为画像待更新，本轮所有动作结束（成功或失败）后再启动画像抓取，避免额外的 Profile / Post 请求插到关注和回复之间。画像任务不继承已结束监听的请求取消条件，保持独立状态和原运行追踪 ID；手动更新画像照常启动。

画像长度只由生成提示词建议 150～250 字，不按字数或输出文本 token 数拒绝结果或截断内容；继续验证 JSON 结构和证据来源。手动编辑支持长文和多段文字，保存只写本地数据库，不调用 AI 或 X。监听画像在 `account_profiles.value` 中保留原始编辑文本 `portraitText`，结构化 `memory` 继续供判断与回复使用；原画像依据另存 `evidenceIds`，编辑和清空不会删除依据，归档清理也须保护这些帖子。重新生成成功后替换画像及依据，失败保留原值。

关注画像在 `following_users.value` 中保存 `summary` 和 `summaryEvidence`（引用的原帖快照），按自己的 actor ID 隔离。旧记录未保存的依据不补抓；下一次明确更新时记录。手动保存必须校验条目归属，画像待生成或生成中拒绝并发保存，防止被后台结果覆盖。前端轮询不能覆盖未保存的草稿；只有用户确认的重新生成成功后才替换草稿。

## 账号和外部请求

配置主键标识自己的账号，稳定 X actor ID 隔离请求额度和关注关系，目标用户 ID 标识对方；用户名可变，不能把用户名当作稳定身份。每轮监听选定一次账号，由同一账号完成读取与动作。统一列表中的操作使用条目账号，不使用顶部筛选值。

首页、Profile、用户 Post、关注、取消关注、回复都有按账号共享的每日额度；复用现有请求入口，不能绕过额度。关系核对优先读取同一账号视角的 Profile，校验目标 ID。外部写入前持久化待确认状态；超时或结果不明保留待核对记录，不重复发送。

X 客户端统一通过 `XRequestQueue.request` 检查发送条件。监听（包括手动“立即执行一次”）、连续互关动作、自动画像任务在 `withQueuedXRequests` 范围内运行，它们的真实 X 请求跨账号、跨任务共用串行队列：上一次排队请求结束（含失败）后，至少间隔 **10 秒**。手动单次核对关系、账号测试、添加／取消关注、画像更新，以及聊天所需的 Profile 查询直接发送，不等待任务队列，也不重置该队列的间隔。操作内部的账号互斥和重复提交保护仍保留；手动请求不会绕过正在进行的同账号关系操作。AI、Telegram 和本地数据库操作不经过 X 队列。

两条发送路径都在实际请求前校验凭证、取消条件和每日额度，并原子扣除额度；排队期间不扣额度。手动超额返回 `ACCOUNT_DAILY_LIMIT` / HTTP 429，说明账号、行为、已用额度与恢复时间；聊天发帖权限查询不能吞掉该错误。手动异步画像更新先只读检查 Profile 与 Post 额度，超额立即拒绝且不改画像状态，真正发送时仍重新检查、扣除；等待期间额度变化导致的失败写入画像错误供页面展示。请求超时从发送后开始计时，服务停止取消未发送请求，不自动重发不确定的外部动作。动作层不叠加休眠；AI 与本地处理经过的时间计入任务 X 请求间隔，下一次仅等剩余时间。

回复目前使用 X 网页端 `CreateTweet` GraphQL 接口，关注／取消关注使用网页端关系接口；服务端携带账号凭证请求，不是真实浏览器点击，也不是官方开发者 API。改请求方式时同步更新这些说明。

`observability/trace.ts` 统一记录外部请求及执行链路，使用异步上下文隔离任务、账号、帖子和请求 ID。监听、手动接口、后台画像复用同一个日志入口；curl 必须在队列校验和额度检查通过后的真实发送点生成，保留实际参数，不能为了诊断额外发送请求。日志输出不参与业务成败或重试判断。按用户明确要求，生产启动入口默认保留完整凭证和原始内容，具体查看方式及边界见 [请求链路日志](development.md#请求链路日志)。

首页监听按本任务已处理 Post ID 去重，不按发布时间或任务创建时间过滤。指定用户监听仅请求 Post 时间线，不请求 Reply 时间线；响应中夹带的 Reply 也不进入监听判断。每轮最多 5 次 Post 分页请求，Profile 查询不占分页次数。正常轮次从最新页开始，以本任务上次完整处理的 `lastSeenPostId` 为边界，只判断 ID 更大且未处理的帖子。当前页的正常时间线 Post 出现小于或等于边界的 ID，处理完整当前页的新帖后停止翻页；边界本帖删除时仍可用较小 ID 停止。不以一条旧帖为由跳过同页其他新帖。解析器单独返回 `boundaryPostIds`，仅普通顶层原帖可充当边界或推进最高 ID，置顶、广告、转发和会话上下文不能触发提前停止。空页、只有 Reply 或上下文的页仍按下一页游标继续；无下一页停止，重复游标报错。

边界存于 SQLite `workflows.value` 的 `lastSeenPostId`；`workflow_seen` 继续保存任务级逐帖去重记录。从旧版升级时，仅从该任务已处理且归档的原始 Post 恢复边界，排除 Reply 和未处理帖子；没有可靠记录时使用空边界，原配置、画像和去重记录保留。迁移只执行一次（`workflow_posts_only_cursor_v1`），上线前备份数据库。首次无边界时最多读取 5 页历史，成功处理后建立当前最高 Post ID，不继续遍历更早历史。

已存在边界但 5 页内未追赶到旧边界时，本轮正常处理已获取内容，在 `workflows.value.postScan` 保存下一页游标、待提交最高 Post ID 和执行账号；保持 `lastSeenPostId` 不变。下一轮用相同账号继续该窗口，到达旧边界或末页后才提交最高 ID，后续恢复从最新页读取，避免超限造成中间漏帖。切换目标或来源清除两种进度，切换账号清除续页游标；随机执行账号不同也从首页重抓以避免混用游标。AI、分页或动作失败不提交新的边界或续页状态，已有逐帖去重防止重复执行。日志的 `timeline.fetch.finished.reason` 区分 `boundary_reached`、`no_next_page` 和 `page_limit`，附旧边界、待提交边界与续页游标。

所有后端 AI 请求统一向上游发送 `stream: true` 和 `Accept: text/event-stream`，包括监听判断、画像、回复生成、侧边栏对话、翻译与 AI 服务测试。`OpenAICompatibleClient.complete` 仍返回完整字符串：内部增量接收 SSE，确认正常结束后再交给业务解析，不能收到半截 JSON 就更新进度或执行动作。原有前端一次返回完整内容的接口保持不变，已有逐段输出接口共用解析器。OpenAI 的正文取 `delta.content`，Anthropic 取文本块及文本增量；推理、工具参数等非正文不拼入结果。解析器处理中文跨字节拆包、SSE 多行数据和 CRLF；格式错误、读流失败、缺少结束标记或非正常结束均失败。`length` / `max_tokens` 保留原有最多一次扩容重试，丢弃上次残片并共用原始总超时；已向前端输出的流不自动重播。HTTP 504 或网络中断不自动重试。少数兼容网关忽略流式参数而返回完整 JSON 时，只读取当前响应，不重新发送非流式请求。

流式接收不改变按批判断、账号限额和 X 队列。监听判断的 180 秒预算覆盖连接与读流；其他操作保留各自原有总预算，不因心跳无限延长。此改动可减少等待完整非流式结果造成的空闲，但不能保证上游不再超时。结束语义参考 [OpenAI Docs：Chat Completions streaming events](https://developers.openai.com/api/reference/resources/chat/subresources/completions/streaming-events)。

AI 监听按批分析，按条数和输入预算分批；模型只返回确定命中的 `matches`，每项给出原始字符串 ID 和简短依据，不输出未命中项或画像。没有命中返回 `{"matches":[]}`。服务端完整验证 JSON、ID、重复项及证据后，把本批省略的 ID 补为内部未命中结果，再统计、去重与执行动作；截断、缺字段、未知 ID 等无效结果不能当作空命中。匹配结果格式不合法最多修正重试一次，网络或超时不在批处理层再次重试；底层 AI 客户端只保留原有的一次截断扩容重试。画像输出不合法直接失败，等待下次手动更新（关注列表仍按原有画像状态处理）。状态显示当前批次、本轮累计扫描数、AI 命中数和处理完成数。失败或 AI 输出截断不能悄悄跳过内容、推进监听偏移量或显示完成。

包含“关注作者”的编排仅在本次新关注成功后允许后续回复。首页快照显示已关注、当前账号关注列表已有关注，或记录为已取消关注时，直接跳过；`not_following` 是自动化的退出信号，不能由自动任务重新关注。未记录的目标在关注前读取最新 Profile，避免快照过期；其他账号的关系不影响当前账号。待核对的记录也不自动重发。只有明确的手动添加关注能覆盖退出状态。

新关注的动作结果保存 `newlyFollowed`，按 actor ID 串行确认与关注，同一作者多条帖子或并发任务只由建立新关系的那条记录继续回复。因额度不足暂缓的回复，只能凭该记录保存的新关注证明恢复；旧记录的“已经关注”不能算证明。回复生成前和排队发送前都检查是否已取消关注。跳过显示为“已跳过”，不算完成；`WorkflowRun.matched` 保留动作资格计数（关注编排需新关注成功），`aiMatched` 独立统计有效 AI 命中，`scanned` 按本轮检查的帖子 ID 去重，包含后续过滤跳过的帖子。界面统一显示 `scanned`、`aiMatched`、`completed` 的本轮累计值；复核不重复计数。回复失败不抹掉已经成功的新关注，也不自动重发。

## 改表与兼容

用户允许调整现有表结构。能保留的配置尽量保留；无法合理兼容的内容明确记录处理结果，避免让迁移包袱主导新设计。验证真实配置保留情况时只输出数量与安全字段，禁止输出 Cookie、API Key 或完整设置。历史方案不要求重新恢复已删除的功能入口。
